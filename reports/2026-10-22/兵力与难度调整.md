# 兵力与难度调整

日期：2026-10-22。以已发布 `main` 的 `a632ea3` 为基线，在 `codex/army-count-hardmode` 工作树实现。

## 调整

- 冲锋和无尽人数上限从 280 降到 60；防线从无实际限制改为 64。限制的是实际战斗人数和界面数字，并非只减少渲染模型。
- 加人门起始值、射击增长速度、乘法门倍率都收紧。门的每次增长基础命中数从第 1 关的 4.5 提到 6.5，正数增长系数从 1.23 提到 1.32；防线乘法门从 ×1.5 改成 ×1.25。冲锋中期的 ×2 门改为 ×1.5，部分 ×1.5 门改为 ×1.25。
- 人质笼从约 `2 + L + 当前估算人数×8%` 改为约 `1 + L/3 + 当前估算人数×2.5%`；防线装甲障碍、中途 Boss 援军和重复武器奖励也同步缩小。第 1 关开局的较大门保留，让初始 1 人有机会站稳。
- 较小队伍下重新校准敌人和 Boss 的血量预算。防线后期双 Boss 血量增长放缓，避免人数上限让第 10 关成为固定死关。第 1 关冲锋 Boss 稍微缩短，较小队伍仍要持续作战，但不会因人数减少而拖得过长。
- 成长模拟增加 `@peak` 行，记录每关全部尝试的峰值人数中位数、P90 和最大值。

`npm run sim:progress -- 8 5 0.12 0`：5 名从零升级的自动驾驶玩家都打通前 8 关；各关重试次数中位数为 2 / 4 / 6 / 7 / 2 / 5 / 5 / 3，峰值人数每关都不超过 64。`npm run sim:progress -- 16 3 0.12 0`：3 名玩家都打通前 16 关，每关至多尝试 11 次；第 12–13 关仍有 9–11 次的高重试个例。

`npm run sim -- campaign 8 6`：正常升级时第 1–8 关胜率为 83% / 83% / 83% / 100% / 83% / 100% / 100% / 67%，第 6 关峰值达到 60 人上限。`npm run sim -- endless 5 6`：按第 5 关升级的 6 个种子跑出 547–786 米。

`npm test`：35 项通过。`npm run build`：TypeScript 检查和生产构建通过。`npm run smoke -- http://127.0.0.1:5174/ work/shots/army-count-final`：390×844 桌面 Chrome 手机视口下，主页、防线、冲锋首关 Boss、结算和防线 Boss 场景均完成，未见控制台错误；3 个 FPS 采样点均为 61。检查截图时，防线第 6 关界面显示 64 人上限。桌面采样不能代表 iPhone Safari 的帧率或发热。

这些是自动驾驶的固定种子结果。它会主动选门、避开预警，不能代替真人触控和实机性能验收。

## 设计依据

[Unity 的游戏经济平衡指南](https://unity.com/how-to/design-balanced-in-game-economy-guide-part-3)建议考虑不同玩家的行为、逐步引入难度，并反复测试奖励与成长。这里的上限、奖励和血量都是本项目的设计取值；上述模拟用于检验其相互作用，Unity 没有给出这些具体数字。
